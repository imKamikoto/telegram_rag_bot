## Общее описание проекта

RAG-система для быстрого поиска по корпоративной документации. Взаимодействие осуществляется через Telegram-бот. Система поддерживает загрузку документов форматов MD, PDF, DOCX, разделение документации на базы знаний (HR, IT, Legal, Finance и др.), ролевую модель (Admin / User) и семантический кэш для ускорения повторных запросов. Административное управление — через веб-интерфейс (Mini App / REST API).

## 4. Расчёт ресурсов

**Технологический стек inference:**
- LLM: Ollama (Llama 3.1 8B / Mistral 7B, q4-квантизация) через LiteLLM proxy
- Embedding: Ollama (mxbai-embed-large, 1024 dim)
- Всё inference локально — нет зависимости от внешних API

### 4.1 Базовые параметры нагрузки

| №  | Характеристика | Значение | Ед. изм. |
|----|----------------|----------|----------|
| 1  | MAU | 1 000 | чел. |
| 2  | DAU | 300 | чел. |
| 3  | Запросов от 1 пользователя в день | 15 | шт. |
| 4  | Всего запросов в день | 4 500 | шт. |
| 5  | RPS (пик, активные часы = 8 ч) | 4500 / 8 / 3600 ≈ 0,16 → пик ×3 ≈ **0,5** | RPS |
| 6  | Запросов одновременно в обработке (пик) | 0,5 RPS × 7 сек ≈ **4** | шт. |

| # | Характеристика | Расчёт | Значение |

**Внутренний трафик (App ↔ LiteLLM ↔ Ollama, Docker network):**

| Шаг | Направление | Размер |
|-----|-------------|--------|
| Embedding вопроса (запрос) | App → Ollama | 0,5 КБ |
| Embedding вопроса (ответ) | Ollama → App | 4 КБ |

При кэш-хите: только embedding → **~4,5 КБ**.
Принимая долю кэш-хитов ~40%: `0,4 × 4,5 + 0,6 × 29,5 ≈ 19,5 КБ/запрос` → **~78 Кбит/с** внутреннего трафика.

## 5. Конкретный High-level Design (Concrete HLD)

**Docker Compose — 6 контейнеров:**

| Контейнер | Образ | Ресурсы | Назначение |
|-----------|-------|---------|------------|
| app | python:3.12-slim | CPU, ~512 МБ RAM | FastAPI + aiogram (монолит) |
| postgres | postgres:16 + pgvector | CPU, ~1 ГБ RAM | Реляционные данные + векторный поиск |
| redis | redis:7-alpine | CPU, ~256 МБ RAM | Semantic cache + chat sessions |
| minio | minio/minio | CPU, ~512 МБ RAM | S3-совместимое хранилище документов |
| litellm | litellm/litellm | CPU, ~256 МБ RAM | OpenAI-compatible proxy для LLM |
| ollama | ollama/ollama | **GPU**, ~12–16 ГБ VRAM | LLM + Embedding inference |

**Обоснование ключевых компонентов:**

- **MinIO** — S3-совместимый object storage для хранения оригинальных файлов документов. Обеспечивает presigned URLs (TTL 1 ч) для прямой доставки источников пользователю. Код работает через boto3 — миграция на AWS S3 / Yandex Object Storage выполняется заменой endpoint URL.
- **LiteLLM** — унификация API. Приложение работает с OpenAI-совместимым API; переход на облачный LLM (OpenAI, Anthropic, OpenRouter) — только конфиг LiteLLM.
- **Redis** — semantic cache с cosine similarity (~1 мс vs 10–50 мс у pgvector), TTL для chat sessions из коробки. При падении Redis система работает в degraded mode (без кэша).
- **pgvector с HNSW** — векторный поиск top-5 чанков прямо в PostgreSQL; отдельный Vector DB не требуется для данного масштаба.

## 7. Low-level Design (C4 Component)

### 7.1 Протоколы и порты

| Связь | Протокол | Порт | Формат данных |
|-------|----------|------|---------------|
| Telegram → nginx | HTTPS | 443 | JSON (Bot API) |
| nginx → app | HTTP | 8000 | JSON |
| app → PostgreSQL | TCP (libpq) | 5432 | SQL / pgvector |
| app → Redis | TCP (RESP) | 6379 | Redis protocol |
| app → MinIO | HTTP (S3 API) | 9000 | Binary (boto3) |
| app → LiteLLM | HTTP | 4000 | JSON (OpenAI-compatible) |
| LiteLLM → Ollama | HTTP | 11434 | JSON (Ollama API) |

### 7.2 Потоки данных

**Поток A — Запрос пользователя (ФТ-1):**

```
User → Telegram → nginx(:443) → app(:8000)
  → [Auth] PG(:5432): проверка user + KB доступ
  → [RAG] Ollama(:11434): embedding вопроса (через LiteLLM)
  → [RAG] Redis(:6379): поиск в semantic cache (cosine similarity ≥ 0,92)
       ├─ HIT  → presigned URL (MinIO) → ответ пользователю (≤200 мс)
       └─ MISS:
            → PG(:5432): pgvector top-5 чанков
            → Redis(:6379): загрузка контекста сессии
            → Ollama(:11434): генерация ответа (LLM)
            → MinIO(:9000): presigned URL документов-источников (TTL 1 ч)
            → Redis(:6379): сохранить в cache + обновить сессию
            → PG(:5432): сохранить chat_message
            → ответ + ссылки → Telegram (3–10 сек)
```

**Поток B — Загрузка документа (ФТ-3):**

```
Admin → app(:8000)
  → [Auth] PG(:5432): проверка admin + KB доступ
  → MinIO(:9000): PUT оригинал файла
  → PG(:5432): INSERT document (status='processing')
  → MinIO(:9000): GET файл для парсинга
  → парсинг (PyPDF2 / python-docx / markdown)
  → chunking (500 токенов, overlap 50)
  → Ollama(:11434): batch embedding чанков
  → PG(:5432): INSERT chunks + vectors
  → PG(:5432): UPDATE document (status='ready')
  → Redis(:6379): инвалидация cache для KB
  → уведомление Admin
```

## 8. Расчёт доступности

### 8.1 Целевой показатель

**НФТ-3:** доступность 99,5% (допустимый downtime ~3,65 дня/год).

### 8.2 Компоненты и их MTBF / MTTR

| Компонент | MTBF | MTTR | Доступность |
|-----------|------|------|-------------|
| app (FastAPI) | 720 ч | 0,5 ч | 99,93% |
| PostgreSQL | 2 160 ч | 1 ч | 99,95% |
| Redis | 4 320 ч | 0,25 ч | 99,99% |
| MinIO | 2 160 ч | 0,5 ч | 99,98% |
| Ollama (GPU) | 720 ч | 2 ч | 99,72% |
| LiteLLM proxy | 2 160 ч | 0,25 ч | 99,99% |
| Docker host (OS + hardware) | 2 160 ч | 1 ч | 99,95% |

### 8.3 Системная доступность

Все компоненты работают в последовательной цепочке (single-node), поэтому:

```
A_system = A_app × A_pg × A_redis × A_minio × A_ollama × A_litellm × A_host
         = 0,9993 × 0,9995 × 0,9999 × 0,9998 × 0,9972 × 0,9999 × 0,9995
         ≈ 0,9951 = 99,51%
```

**Результат: 99,51% > 99,5% (НФТ-3 выполняется с минимальным запасом)**

Основной вклад в недоступность вносит **Ollama** (GPU-ноды) — MTBF 720 ч (~1 месяц): перегрев, OOM при пиковой нагрузке, обновление драйверов. Деградированный режим при недоступности Ollama: возврат 503 на LLM-запросы при сохранении работоспособности CRUD-операций.

### 8.4 Допустимый downtime

| Период | Допустимый downtime (99,5%) | Фактический (расчётный, 99,51%) |

| Час | 1,8 мин | 1,76 мин |
| Сутки | 7,2 мин | 7,06 мин |
| Месяц | 3,6 ч | 3,53 ч |
| Год | 43,8 ч | 43,0 ч |

## 12. Анализ узких мест и обходные решения (Work-around)

### 12.1 Основной bottleneck — Ollama (однопоточный GPU-inference)

**Проблема:** Ollama обрабатывает запросы последовательно на одном GPU. При параллельных запросах они выстраиваются в очередь, что приводит к экспоненциальному росту хвостовых задержек:

| Нагрузка | p50 /ask | p95 /ask |
|----------|----------|----------|
| 5 пользователей (smoke) | ~80 мс | ~400 мс |
| 20 пользователей (load) | 320 мс | 1 900 мс |
| 50 пользователей (stress) | 410 мс | 11 000 мс |

**Причина роста p50:** при 20+ параллельных пользователях запросы к Ollama ждут освобождения GPU. Каждый LLM-inference занимает ~2–4 сек → очередь накапливается.

**Work-around 1 (текущий): Semantic cache в Redis**
- Cosine similarity ≥ 0,92 (128-мерный вектор), TTL 24 ч
- Кэш-хит: ~130 мс (только embedding, без LLM) vs ~3–7 сек (LLM-inference)
- При 40% cache hit rate: среднее время ответа снижается с ~5 сек до ~2,5 сек
- Инвалидация при загрузке/удалении документа

**Work-around 2 (рекомендуемый): Переход на OpenRouter / облачный LLM**
- LiteLLM proxy уже интегрирован — смена backend занимает минуты (правка конфига)
- OpenRouter / Together AI / Groq: параллельные запросы, auto-scaling
- Ожидаемый p95 при 50 пользователях: < 3 сек (vs 11 сек на Ollama)
- Компромисс: стоимость (~$0,0015/1K токенов для Llama 3.1 8B на OpenRouter)

**Work-around 3 (продвинутый): vLLM вместо Ollama**
- Continuous batching: несколько запросов обрабатываются одновременно на одном GPU
- При 16 ГБ VRAM: throughput ×3–5 vs Ollama
- Поддерживается через LiteLLM

### 12.2 Гонка admin-токенов при параллельных воркерах

**Проблема:** API хранит один активный токен на `telegram_id` в Redis (`admin_token_user:{telegram_id}`). При нескольких параллельных admin-воркерах с одним telegram_id каждый новый `/auth/admin-token` инвалидирует токен предыдущего → 401 на следующем запросе.

**Work-around (реализован):**
1. Пул из 5 уникальных admin-пользователей (`7_000_000_001–7_000_000_004` + основной)
2. Атомарный счётчик + `threading.Lock` — гарантирует уникальное назначение admin на воркер без коллизий
3. `make setup-admin` — DDL-вставка admin-пользователей в БД после каждого `docker compose down -v`

### 12.3 MinIO presigned URL — race condition при удалении документа

**Проблема:** При удалении документа из базы знаний объект удаляется из MinIO, но существующие presigned URLs остаются активными в кэше Redis до истечения TTL. Пользователь может получить ответ со ссылкой на уже удалённый файл → 403/404 при переходе.

**Work-around (реализован):**
- Инвалидация cache по KB при удалении любого документа (`DEL cache_index:{kb_id}` + связанные ключи)
- TTL presigned URL — 1 ч (короткий, снижает окно некорректных ссылок)

**Полное решение (рекомендуемое):** хранить presigned URL не в кэше, а генерировать их при каждом запросе ответа (lazy generation). Overhead незначителен (~5 мс на boto3-вызов).

### 12.4 SequentialTaskSet — повторная регистрация изолированного пользователя

**Проблема:** В Locust `SequentialTaskSet.on_start()` вызывается один раз при первом запуске. При повторном цикле (после шага 9 — удаления изолированного пользователя) шаг 5 (`GET /users/telegram/{id}`) возвращает 404, и весь цикл сбоил.

**Work-around (реализован):**
- В шаге `grant_access()` при 404 — повторная регистрация изолированного пользователя через bot-заголовки
- `resp.success()` при 404 — не считается ошибкой (штатная ситуация второго цикла)

### 12.5 Коллизии telegram_id пользователей

**Проблема:** При ограниченном пуле тестовых telegram_id (например, 2 ID на 20 воркеров) несколько воркеров регистрировались под одним ID. При этом последний воркер перезаписывал привязку KB, предыдущие получали 403 на `/ask`.

**Work-around (реализован):**
- Каждый воркер генерирует уникальный telegram_id: `random.randint(8_000_000_000, 8_999_999_999)`
- Вероятность коллизии: 1/10^9 при 50 воркерах ≈ пренебрежимо мала
- Три непересекающихся диапазона: `7_xxx` (admin pool), `8_xxx` (user scenario), `9_xxx` (admin isolated user)

| НФТ-8: TTL инвайт-кодов | ✅ | Реализовано; многоразовые коды — опция |

### 13.2 Технические достижения

1. **Полный RAG-pipeline** на локальном стеке: embedding → vector search → semantic cache → LLM → источники с presigned URL
2. **Semantic cache** в Redis снижает нагрузку на Ollama на ~40% и уменьшает latency кэш-хитов в ~10 раз
3. **pgvector HNSW** — векторный поиск без отдельного Vector DB, прямо в PostgreSQL
4. **LiteLLM proxy** — swap-ready: смена LLM-провайдера без изменений в коде приложения
5. **Нагрузочные тесты**: 0% ошибок в пользовательском сценарии при 20 и 50 пользователях

### 13.3 Ограничения текущей реализации

1. **Single-node архитектура** — нет горизонтального масштабирования. Для 1000 пользователей потребуется либо vLLM с continuous batching, либо облачный LLM.
2. **Ollama — однопоточный inference** — основной bottleneck при ≥20 RPS на /ask. p95 растёт нелинейно с ростом конкурентности.
3. **Отсутствие retry/circuit breaker** — при кратковременном сбое Ollama запрос возвращает 500 без повтора.
4. **Отсутствие мониторинга** — нет Prometheus/Grafana; диагностика только через логи контейнеров.

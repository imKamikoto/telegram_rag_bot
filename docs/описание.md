## Общее описание

RAG система для организации документации компании. Система для быстрого взаимодействия с документацией по методологии RAG. Взаимодействие с системой осуществляется посредством Telegram бота. Система предоставляет возможность работать с документами разного формата, такими как: MD, PDF, DOCX — самые распространённые форматы для написания документации. Также система предоставляет возможность разделения областей документации — осуществляется с помощью Баз знаний. Каждая база знаний хранит документацию для определённой области компании, например — HR, IT, Инфраструктура компании и т.п. Есть несколько уровней доступа при взаимодействии с системой — Admin и User. Admin занимается загрузкой документов, предоставлением доступа к чат боту посредством создания кода приглашения. User взаимодействует с базой знаний, к которой у него есть доступ

**4.2.1 Внутренний трафик (App ↔ LiteLLM ↔ Ollama, Docker network)**

На каждый запрос пользователя pipeline выполняет два обращения к Ollama:

| Шаг | Направление | Размер |
| --- | --- | --- |
| Embedding вопроса (запрос) | App → Ollama | 0.5 КБ |
| Embedding вопроса (ответ) | Ollama → App | 1024 × 4 Б = 4 КБ |
| LLM-промпт (запрос) | App → Ollama | system 1 КБ + 5 чанков × 2 КБ + история 10 сообщ. × 1.1 КБ + вопрос 0.5 КБ ≈ **23 КБ** |
| LLM-ответ (ответ) | Ollama → App | ~2 КБ (~500 токенов) |
| **Итого на MISS-запрос** | | **~29.5 КБ** |

При кэш-хите (HIT): только embedding-шаг → **~4.5 КБ**.

Принимая долю кэш-хитов ~40 %:

`0.4 × 4.5 КБ + 0.6 × 29.5 КБ = 1.8 + 17.7 ≈ 19.5 КБ/запрос`

| # | Характеристика | Расчёт | Значение |
| --- | --- | --- | --- |
| 1 | Внутренний трафик (inference, среднее) | 0.5 RPS × 19.5 КБ × 8 | ~78 Кбит/с |
| 2 | Внутренний трафик (все MISS, пессимистично) | 0.5 RPS × 29.5 КБ × 8 | ~118 Кбит/с |
| 3 | Batch-embedding документов | 10 × 20 чанков × (4+4) КБ / 86 400 × 8 | ~0.15 Кбит/с |
| 4 | Соотношение внутренний / внешний | ~80 / ~16 Кбит/с | **~5× больше** |

Примечание: внешний трафик к облачным LLM API отсутствует — Ollama работает локально. Весь inference-трафик идёт через Docker network и не учитывается в счёте за bandwidth.

4.4 Хранилище: PostgreSQL + pgvector

Параметры chunking:

- Средний документ (2 МБ файл): ~20-40 страниц, текстовый контент ~8 000-12 000 токенов
- Размер чанка: ~500 токенов, overlap ~50 токенов → эффективный шаг = 500 − 50 = 450 токенов → `10 000 / 450 ≈ 22` чанков, округляем до **20** (с учётом коротких разделов)
- Размер текста одного чанка: 500 токенов × ~8 байт/токен (кириллица UTF-8, ~1.5 символа/токен × 2 байта) ≈ **4 КБ**

# 5. Concrete High-level Design

![mermaid-diagram-2026-04-17-140109.png](%D0%A2%D1%80%D0%B5%D0%B1%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D1%8F%20%D0%BA%20%D0%BF%D1%80%D0%BE%D0%B5%D0%BA%D1%82%D1%83%20%D0%B0%D0%BF%D1%81/mermaid-diagram-2026-04-17-140109.png)

**Docker Compose — 6 контейнеров:**

| Контейнер | Образ | Ресурсы | Назначение |
| --- | --- | --- | --- |
| app | python:3.12-slim | CPU, ~512 МБ RAM | FastAPI + aiogram (монолит) |
| postgres | postgres:16 + pgvector | CPU, ~1 ГБ RAM | Данные + векторный поиск |
| redis | redis:7-alpine | CPU, ~256 МБ RAM | Semantic cache + chat sessions |
| minio | minio/minio | CPU, ~512 МБ RAM | S3-совместимое хранилище документов |
| litellm | litellm/litellm | CPU, ~256 МБ RAM | OpenAI-compatible proxy |
| ollama | ollama/ollama | **GPU**, ~12-16 ГБ VRAM | LLM + Embedding inference |

**Зачем MinIO (а не локальная ФС):**

- **Presigned URLs** — генерация временных ссылок на документы-источники (ФТ-8). Пользователь кликает ссылку в ответе бота → документ открывается в браузере. TTL 1 час, повторная генерация при повторном запросе
- S3-совместимый API — код работает через boto3. Миграция на AWS S3 / Yandex Object Storage — смена endpoint URL в конфиге
- Веб-консоль (:9001) для просмотра и управления файлами (удобно для отладки и Admin)
- Изоляция данных от Docker volumes — защита от случайного удаления
- Single-node mode — минимальный overhead для корпоративного масштаба

**Зачем LiteLLM:** унификация API. Приложение работает с OpenAI-совместимым API. Если понадобится перейти на облачный LLM (OpenAI, Anthropic, Together) — меняется только конфиг LiteLLM, код приложения не трогаем.

**Зачем Redis (а не только PG):**

- Semantic cache: поиск по cosine similarity среди кешированных вопросов за ~1 мс (в PG pgvector — ~10-50 мс на малых объёмах, но Redis дает стабильный субмиллисекундный доступ)
- Chat sessions: TTL из коробки, автоматическая очистка старых сессий
- При падении Redis: система продолжает работать (degraded mode — без кеша, чуть медленнее)

### 6.2 Физическая модель (DDL)

Детальные определения таблиц с типами и размерами — см. Этап 4 → «Физическая модель ключевых таблиц».

**Индексы:**

| Таблица | Индекс | Тип | Назначение |
| --- | --- | --- | --- |
| users | telegram_id | UNIQUE B-tree | Поиск пользователя по Telegram ID |
| chunks | embedding | IVFFlat (pgvector) | Векторный поиск, `lists=100` |
| chunks | document_id | B-tree | Удаление чанков при удалении документа |
| documents | knowledge_base_id | B-tree | Список документов в KB |
| chat_sessions | user_id, knowledge_base_id | Composite B-tree | Поиск сессий пользователя |
| chat_messages | session_id | B-tree | Загрузка истории сессии |
| invite_codes | code | UNIQUE B-tree | Валидация инвайт-кода |
| user_knowledge_bases | user_id, knowledge_base_id | UNIQUE Composite | Проверка доступа (часто) |

**Партиционирование:** не требуется для сценария A (объёмы позволяют работать без партиций).

### 6.3 Модель данных Redis

| Ключ | Тип | TTL | Содержимое |
| --- | --- | --- | --- |
| `cache:{kb_id}:{embedding_hash}` | Hash | 24ч | `{answer, sources_json, embedding_vector}` |
| `session:{session_id}` | List | 2ч | Последние 10 сообщений сессии (role + content) |
| `cache_index:{kb_id}` | Set | — | Множество embedding_hash для данной KB (для инвалидации) |

**Инвалидация кеша:** при загрузке/удалении документа в KB → `DEL cache_index:{kb_id}` + удаление всех связанных `cache:{kb_id}:*`.

# 7: Low-level Design (C4 Component)

### 7.2 Протоколы и порты (сводка)

| Связь | Протокол | Порт | Формат данных |
| --- | --- | --- | --- |
| Telegram → nginx | HTTPS | 443 | JSON (Bot API) |
| nginx → app | HTTP | 8000 | JSON (проксирование) |
| app → PostgreSQL | TCP (libpq) | 5432 | SQL / pgvector |
| app → Redis | TCP (RESP) | 6379 | Redis protocol |
| app → MinIO | HTTP (S3 API) | 9000 | Бинарные файлы (boto3) |
| app → LiteLLM | HTTP | 4000 | JSON (OpenAI-compatible API) |
| LiteLLM → Ollama | HTTP | 11434 | JSON (Ollama API) |

### 7.3 Потоки данных (sequence)

**Поток A: Запрос пользователя (ФТ-1)**

```
User → Telegram → nginx(:443) → app(:8000)
  → [Auth] PG(:5432): проверка user + KB доступ
  → [RAG] LiteLLM(:4000) → Ollama(:11434): embedding вопроса
  → [RAG] Redis(:6379): поиск в semantic cache
       ├─ HIT → формирование ответа (+ presigned URLs) → Telegram (≤200 мс)
       └─ MISS:
            → [RAG] PG(:5432): pgvector поиск top-5 чанков
            → [RAG] Redis(:6379): загрузка контекста сессии
            → [RAG] LiteLLM(:4000) → Ollama(:11434): генерация ответа
            → [RAG] MinIO(:9000): presigned URL для документов-источников (TTL 1ч)
            → [RAG] Redis(:6379): сохранить в cache + обновить сессию
            → [RAG] PG(:5432): сохранить chat_message
            → ответ + ссылки на документы → Telegram (3-10 сек)
```

**Поток B: Загрузка документа (ФТ-3)**

```
Admin → Telegram (файл) → nginx(:443) → app(:8000)
  → [Auth] PG(:5432): проверка admin + KB доступ
  → [Doc] MinIO(:9000): PUT оригинал в bucket documents/{kb_id}/{doc_id}
  → [Doc] PG(:5432): INSERT document (status='processing', s3_key)
  → [Doc] MinIO(:9000): GET файл для парсинга
  → [Doc] парсинг (PyPDF2/python-docx/markdown)
  → [Doc] chunking (500 токенов, overlap 50)
  → [Doc] LiteLLM(:4000) → Ollama(:11434): batch embedding чанков
  → [Doc] PG(:5432): INSERT chunks + vectors
  → [Doc] PG(:5432): UPDATE document (status='ready')
  → [Doc] Redis(:6379): инвалидация cache для KB
  → уведомление Admin → Telegram
```

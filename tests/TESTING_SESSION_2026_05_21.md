## Найденные проблемы

### 1. Admin token протухает / удаляется

**Симптом:** `GET /api/v1/stats → 401 "User not found"`

**Причина:** Токен в Redis жив, но пользователь удалён из таблицы `users`.
Удалял его сам admin-сценарий в **шаге 9** (удалить пользователя) — он брал
`TEST_TELEGRAM_IDS[0]`, который совпадает с реальным admin-аккаунтом `529936774`.

**Статус:** Пользователь восстановлен через прямой INSERT в БД.
Корневая причина устранена (см. фикс ниже).

---

### 2. 403 "Нет доступа к базе знаний" — коллизия telegram_id

**Симптом:** 65–68% ошибок на `/ask` и `/queries`

**Причина:** В `user_scenario.py` `telegram_id` выбирался из `TEST_TELEGRAM_IDS`
(всего 2 ID на 20 виртуальных пользователей). Несколько воркеров делили один ID,
но регистрировались в разных KB → БД ассоциировала пользователя с последней KB →
остальные воркеры с тем же ID получали 403.

**Статус:** Исправлено.

---

### 3. Admin-сценарий разрушал состояние user-сценария

**Симптом:** Волна 401 "User not found" по всем user-эндпоинтам через ~30с после старта

**Причина:** Admin шаг 9 (`delete_user`) удалял `TEST_TELEGRAM_IDS[0]`,
которого активно использовал user-сценарий. Admin шаг 5 (`grant_access`)
выдавал ему доступ к тестовой KB, засоряя его профиль.

**Статус:** Исправлено.

---

### 4. Cascade failures в admin SequentialTaskSet

**Симптом:** «7. Удалить документ» — 100% ошибок

**Причина:** Если шаг 3 (загрузить документ) или шаг 2 (создать KB) падал,
`created_doc_id = None` → шаг 7 пропускался через `if not self.created_doc_id: return`
но всё равно попадал в статистику как failure из-за предыдущих ошибок в цепочке.

**Статус:** Побочный эффект от проблем 1–3, исправится сам после основных фиксов.

---

### 5. LLM очередь под нагрузкой

**Симптом:** P95 на `/ask` = 1700–2800ms, единичные запросы до 36 сек

**Причина:** Ollama (qwen2.5:7b) обрабатывает запросы последовательно.
Baseline LLM latency (playground, без нагрузки) — **~1.9s p50, ~2.5s p95**.
Под 20 users запросы встают в очередь.

**Статус:** Норма для локального GPU. Решается переходом на OpenRouter.

## Итоговые фиксы

### `user_scenario.py` — синтетические telegram_id

```python
# БЫЛО
self.telegram_id = random.choice(TEST_TELEGRAM_IDS)  # 2 ID на 20 users → коллизии

# СТАЛО
self.telegram_id = random.randint(8_000_000_000, 8_999_999_999)  # уникальный per-worker
```

Каждый виртуальный пользователь регистрируется как новый уникальный аккаунт.
`TEST_TELEGRAM_IDS` и вся логика shared-ID убраны из `config.py`.

---

### `admin_scenario.py` — изолированный пользователь

```python
# on_start: генерируем уникальный ID для этого admin-инстанса
self.isolated_telegram_id = random.randint(9_000_000_000, 9_999_999_999)

# Регистрируем его через бот-хедеры (не через admin token)
POST /api/v1/users  { telegram_id: self.isolated_telegram_id, invite_code: ... }

# Шаг 5 — grant_access работает с isolated_telegram_id (не с TEST_TELEGRAM_IDS[0])
# Шаг 9 — delete_user удаляет isolated_telegram_id (не трогает реальных пользователей)
```

---

### Диапазоны telegram_id (не пересекаются)

| Диапазон | Назначение |
|---|---|
| `< 8_000_000_000` | Реальные Telegram ID (например, `529936774`) |
| `8_000_000_000 – 8_999_999_999` | Синтетические, user-сценарий |
| `9_000_000_000 – 9_999_999_999` | Синтетические, admin-сценарий |
